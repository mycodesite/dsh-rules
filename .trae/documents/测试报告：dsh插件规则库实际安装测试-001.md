## 3. Q2：web 安装与启动（三种路径实测）

### 3.1 路径 A：`link:` 开发链接（本环境 allMemory 所用方式）
```
dsh plugin --profile rbtest add link:O:/mcpFs/dsh-plugin-build/dsh-rules
```
启动后出现**启动报错**（复现用户症状）：
```
[loader-isolation] entry rulebase (rulebase) failed to apply: Error:
Cannot find package '@deepseek-ai/dsh-timeout' imported from
O:\mcpFs\dsh-plugin-build\dsh-rules\node_modules\@deepseek-ai\dsh-llm\lib\index.js
```
- **根因**：`link:` 场景下，rulebase 的 peer（dsh-llm 等）从**插件仓库自身 node_modules** 解析；rulebase 的 devDependencies 集合过小（缺 `dsh-timeout` 等 dsh 运行时依赖），导致传递依赖解析不到，host 半 apply 失败。宿主 web server 仍能启动（规则注入失效、设置项不会注册）。
- 对比：同环境的 allMemory 之所以正常，是因为其 devDependencies 声明了几乎整套 `@deepseek-ai/*`（含 dsh-timeout 等），链接解析时其仓库 node_modules 已有全部依赖。

### 3.2 路径 B：打包 tarball 安装
```
dsh plugin --profile rbtest add file:./rulebase-0.1.0.tgz
```
失败（`ERR_PNPM_NO_MATCHING_VERSION`）：
```
No matching version found for @deepseek-ai/dsh-session@>=0.1.1 <0.2.0-0
  while fetching it from https://mirrors.tencent.com/npm/
latest release is 0.0.1-rc.1; next: 0.1.1-rc.2
```
- **根因**：本机采用 `mirrors.tencent.com/npm` 镜像，`@deepseek-ai` 系列仅发布 rc 版本，`>=0.1.1 <0.2.0-0` 在 pnpm 解析时无匹配稳定版；且该环境实际依赖「healed fallback（profiles/node_modules）」而非 pnpm 完整解析，tarball 安装路径不可用。

### 3.3 路径 C：发布态（构建产物装入 profile node_modules，模拟真实 bundle 安装）
将 `lib/`、`package.json`、`cordis.patch.yml` 放入 `rbtest\..\..\profiles\rbtest\node_modules\rulebase` 并列入 `dsh.profile.bundles` 后启动：
- **host 无任何 apply 报错**。
- **client 已组合并托管**，实测 HTTP：
  - `GET /plugins/rulebase/client.js` → **200**
  - `GET /plugins/rulebase/<随机不存在>` → **404**
  - 根 HTML 的 `__DSH_BOOT__` 图含：
    `{"id":"rulebase","url":"/plugins/rulebase/client.js?rev=d7bc68d586e8","inject":["slots","connection"]}`
- 结合 [client/index.ts](file:///o:/mcpFs/dsh-plugin-build/dsh-rules/src/client/index.ts#L33-L42) 的 `settings.section` 注册逻辑（与已工作插件 allMemory 完全同构），**设置面板「规则」区可正常注册并显示**。
- 注：`/rulebase` RPC 通道以 `authority:'loopback'` 注册，本地 `127.0.0.1/localhost` 访问可通；若经 LAN IP 打开页面则 403（见调查报告中 §3 次要点）。

### 3.4 Q2 小结（根因定位）
- 「web 启动报错 + 设置面板无项」的**直接根因**是 **host 半在 `link:` 安装下无法 apply**（缺 `@deepseek-ai/dsh-timeout` 等传递依赖），host 不生效 → 注入失效、且 client 设置项无从注册。
- 这是**安装形态问题**，不是 `settings.section` 注册代码的问题：改用**发布态安装**后 host/client 均正常（路径 C 实测）。
- **建议修复**：将 `@deepseek-ai/dsh-timeout` 等 dsh 运行时 peer 补进 rulebase 的 devDependencies（参照 allMemory 的完整集），使 `link:` 工作；发布态安装则无需。

## 4. Q3：tui（dsh-tui）与规则管理

- 确认环境具有独立二进制：`@deepseek-harness-tui/dsh-tui`（`dsh-tui.ps1`）。
- tui **无需专门的规则管理界面**：规则唯一事实源是磁盘 `.md` 文件（`~/.dsh/rules` 与 `<cwd>/.dsh/rules`），可直接在终端增删改这些文件。
- 注入机制与 web **一致的部分**：rulebase host 半（systemPrompt 规则段 + `agent/created` 会话钩子 + 文件监听）全部是 cordis host 能力，**与前端形态无关**，只要把 rulebase 列入 tui profile 的 bundle 即生效并即时响应文件变更。
- 不一致/不可用部分（属预期）：client 半声明 `dsh.client.platform:'web'`，tui 无浏览器，因此**无设置面板**（不在 tui 提供规则管理 UI 正是设计预期）。

> 说明：dsh-tui 为交互式终端程序，本次未做无头化启动冒烟（避免交互卡死）；其 host 注入一致性由「平台无关的 cordis host 机制 + 已通过的 web host apply 实测」支撑，属机制级结论。
