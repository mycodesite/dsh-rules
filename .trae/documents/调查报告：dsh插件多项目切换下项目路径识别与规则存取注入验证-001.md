## 1. 背景与目的

此前修复「dsh 启动后未开对话时项目规则无法保存」时，参考 allMemory 插件的工作区/项目路径获取方式，为 rulebase 增加了 `currentCwd` 能力：以 **最近活跃 agent 的 `session.header.cwd`** 作为「当前项目路径」。

本次调查目的：
1. 核实 rulebase 的路径识别机制与 allMemory 的方式是否一致（dsh 启动时以启动目录为工作区、切换项目时经专用函数取项目路径）。
2. 实测 dsh 运行中**在不同项目间切换**时，rulebase 能否正确识别项目路径、正确存取规则、正确注入规则。

## 2. 项目路径识别机制调查

### 2.1 allMemory 的既有方式（上游依据）

allMemory 调查报告/方案（`.trae/documents/调查报告：dsh插件新建对话获取项目路径-001.md`、`解决方案：dsh插件新建对话切换工作记忆库路径-001.md`）确认：

- **数据载体**：每个会话的不可变元数据 `SessionHeader.cwd` 即「该对话创建时所在的项目/工作区绝对路径」；web 模式下新建会话时 cwd 由用户选中工作区的 `path` 解析而来。
- **触发时机**：`agent/session-start`（或 `agent/created`）时读 `agent.session.header.cwd`。
- **兜底链**：显式覆盖 → 会话 cwd → `process.cwd()`（启动目录）。

### 2.2 rulebase 的当前实现（已按同一方式）

- [injector.ts](file:///O:/mcpFs/dsh-plugin-build/dsh-rules/src/host/injector.ts#L73-L80)：`currentProjectCwd()` 从 `activeAgents`（`agent/created` 时以 `agent.session.header.cwd` 记录）倒序取最近非空 cwd。
- [service.ts](file:///O:/mcpFs/dsh-plugin-build/dsh-rules/src/host/service.ts#L35-L37)：`currentCwd` 端点返回 `{ cwd }`；`create/save` 项目级经 `requireProjectCwd` 解析真实 cwd，无 cwd 抛「未选定项目」错误。
- [index.ts](file:///O:/mcpFs/dsh-plugin-build/dsh-rules/src/host/index.ts#L34-L35)：systemPrompt 段 `text` 用 `assembleCtx.agent?.session.header.cwd ?? process.cwd()` 取缓存——与 allMemory 三级兜底一致。
- [paths.ts](file:///O:/mcpFs/dsh-plugin-build/dsh-rules/src/host/paths.ts#L14-L16)：项目规则目录 `<cwd>/.dsh/rules`。

**结论：rulebase 已采用 allMemory 的「会话 cwd 识别项目」机制，dsh 切换项目时新会话的 cwd 由 dsh 从所选工作区解析，rulebase 自动跟随。**

## 3. 实测：多项目切换下的路径识别 / 存取 / 注入

### 3.1 环境准备

- 启动隔离 profile：`dsh --profile rbtest --port 58811 --no-open --host 127.0.0.1`
- 确认插件已生效：`GET /plugins/rulebase/client.js → 200`；`__DSH_BOOT__` 含 `id:"rulebase"`。
- 通过浏览器（browser_use）在工作区之间切换并新建会话，经 RPC 验证 host 侧状态。

### 3.2 实测 1：无活跃会话时 currentCwd

```
POST /rulebase/currentCwd → {"ok":true,"value":{"cwd":null}}
```

✅ 未开对话时返回 `null`，不误指向任意目录；保存兜底弹窗保留。

### 3.3 实测 2：切换项目 → 路径识别跟随

| 步骤 | 操作 | currentCwd 返回 |
|:--|:--|:--|
| a | 浏览器切到 allMemory 工作区、新建会话并发送消息 | `O:\mcpFs\dsh-plugin-build\allMemory` ✅ |
| b | 浏览器切到 dst 工作区、新建会话 | 仍为 allMemory（新会话未真正创建 agent，见 §3.6） |
| c | 浏览器切到 dsh-rules 工作区、新建会话并发送消息 | `O:\mcpFs\dsh-plugin-build\dsh-rules` ✅ |

### 3.4 实测 3：项目规则按项目隔离存取

- 在 allMemory 项目会话下 `create` 项目规则「allMemory项目测试规则」→ 落盘 `O:\mcpFs\dsh-plugin-build\allMemory\.dsh\rules\rule-mtb9j6st.md` ✅
- 查询 dst 项目 `list` → **不包含** allMemory 的规则（返回空/仅既有规则）✅（项目隔离）
- dst 项目既有规则 `rule-mtb86luf.md` 保持独立 ✅

### 3.5 实测 4：规则注入（会话文件核验）

解压会话 `session.jsonl.zstd`，检查组装进 system prompt 的规则段：

- **全局规则注入**（dsh-rules 会话）：
  ```
  ### 全局规则
  #### 提炼共性与特化优化——编写可复用代码
  ...（全局规则全文）
  ```
  ✅ 含「规则库（RuleBase）」引导段 + 全部全局规则。

- **项目规则注入**（allMemory 会话）：
  ```
  ### 项目规则（cwd：O:\mcpFs\dsh-plugin-build\allMemory）
  #### allMemory项目测试规则
  这是 allMemory 项目的专属规则，用于验证项目路径识别。
  ```
  ✅ 项目规则按**当前项目 cwd** 正确注入。

- 交叉佐证：allMemory 会话中模型回复「该目录对应项目规则中识别的 allMemory 项目」——项目规则已被模型感知。

### 3.6 关键发现：新会话懒创建 agent

切换到新工作区的「新会话」**不会立即创建 agent**，只有真正发送消息（触发 `agent/created`）后 `activeAgents` 才记录该 agent 的 cwd，`currentCwd` 随之更新。

- 影响：UI 上切换工作区后、未发送消息前，`currentCwd` 仍指向上一个活跃会话的项目（本例为 allMemory）。
- 属 **dsh 会话机制的正常行为**，非 rulebase 缺陷：规则存取以「真实活跃会话」为准，避免误写。
- 规避：保存前以「当前活跃会话」为唯一依据（rulebase 已如此），设置面板项目 tab 也显示「未选定项目」提示兜底。

## 4. 影响与风险

| 项 | 说明 |
|:--|:--|
| 多项目并存 | 「当前项目」取最近活跃 agent 的 cwd，属合理近似 |
| 会话懒创建 | 新工作区未发消息前 currentCwd 沿用上一项目；保存项目规则时以真实活跃会话为准，不会误写 |
| 兼容性 | `currentCwd` 为新增端点，不影响既有端点 |
| 兜底弹窗 | 无项目时保存仍弹窗提示，作为最后防线保留 |

---

## 5. 结论

1. **路径识别 ✅**：rulebase 采用 allMemory 的「会话 cwd 识别项目」方式，dsh 切换项目后 `currentCwd` 准确跟随活跃会话的项目路径。
2. **规则存取 ✅**：项目规则写入对应 `<项目>/.dsh/rules`，项目间隔离正确。
3. **规则注入 ✅**：全局 + 项目两级规则均注入 system prompt，且项目规则标注 `（cwd：…）`，随项目切换自动切换。
4. **兜底保留 ✅**：未选项目（无活跃 agent）时保存弹窗提示仍生效。
