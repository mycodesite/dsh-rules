规则库更新注入机制

"[规则已更新]" 由 RuleInjector.reload() 无条件注入 —— 每批跨防抖窗口的文件操作 = 一条注入，无内容比对去重。
注入链路 Flow · 规则文件变化 → 对话浮现
触发源 · 双通道叠加
1
主通道 fs.watch：监听全局 ~/.dsh/rules 与项目 <cwd>/.dsh/rules（injector.ts:113-146，默认只监听直接子项），任何规则文件变化经 150ms 防抖（injector.ts:148-155）触发 reload。注意：归档（Move-Item 到 archive/）会在源目录产生"删除"事件，必然触发。
2
次通道 UI 显式 reload：设置面板 create/save/remove 成功后 service.ts:22 显式调 reload——与 fs.watch 双通道叠加，时序错开时同一次保存可能注入两条。
3
注入语义：reload()（injector.ts:90-110）重算规则缓存后，对 activeAgents 中每个活跃 agent 无条件 agent.inject 一条"规则已更新"（第 100 行）；无内容差异比对、无已通知标记。
为何连续三次 · 机制必然推论
·
防抖只合并 150ms 内同批事件；每批跨过防抖窗口的文件操作 → 一次 reload → 一条注入。任务001 实际归档了两个规则文件（rule-任务001-项目切换跟随机制调查.md、rule-任务001-方案定案与实施循环.md）→ 两次 Move-Item 各触发源目录删除事件；叠加最后一次规则文件编辑 → 三批操作 = 三条注入。
·
agent.inject 为不唤醒的排队消息（dsh-agent README.zh.md:72），多次注入在对话流的 pre-step 边界连续浮现多条——与观察到的连续三次一致。归档后规则从合成文本消失属预期（store.list 平铺 readdir 不递归 archive）。
抑制失效原因 · 改进建议
项现状为何失效
并发锁 reloadPending只合并"进行中"的 reload三次 reload 先后完成、互不重叠，各注入一条
150ms 防抖只合并单批事件跨窗口的操作批各自触发完整 reload
内容快照对比无任何文件变化（含归档删除）都注入，不判内容是否真变
通知时间窗无无每 agent 节流
★
首选改进（报告 §八）：在 reload()（injector.ts:90-110）内做新旧合成文本对比，无变化则跳过 inject——单点改动根治无效注入；其次每 agent 通知节流（2s 窗口合并）；tests/ 无 injector 测试，建议补三个用例。
